# Test4：恢复语言漏检与可变字体漏字重的槽位

## 问题

Test3 新增的 XML 保护规则把非纯 `zh` 的语言标签直接转换为整文件保护。
这会在读取实际字形覆盖前排除 `lang=en`、`lang=en-Latn` 的英文 UI 字体，
也会排除同时被中文、日文、韩文 family 引用的同一份中文字库。升级扫描还会
把这些路径从已有清单中移除。这是漏检回归，不应被解释为正常的字体保护。

用真实 DejaVu Sans 和 Noto Sans CJK SC 字体运行完整扫描器，在四种布局下
均复现 Test2 的 2 个槽位在 Test3 降为 1 个；保底 UI 字体始终存在。
这证明代码规则有问题，不能据此认定用户手机减少的具体路径。

字重链路另有真实可达问题：实际 HyperOS 映射器接收 `wght=100..900` 的
可变字体后可能只建立 `regular.font` 和 `variable.font`。后续度量批处理仅查
找已生成的字重锚点，把原本可实例化的 Medium 错当作缺失。用带真实 `gvar`
变化的字体经过实际映射器复现，3 个槽位被减成 2 个；补上同源 500 实例后
恢复 3 个。这与仅含静态 Regular、确实没有其他字重的情况不同。

## 修复与升级

语言标签不再单独否决整个文件。扫描综合实际文字覆盖和所有 XML 引用用途，
恢复英文 UI 和共享中文字库，同时保持独立专用文字、符号、Emoji 等保护。
扫描器修订号升至 8，旧 v7 清单必须重新扫描；同版本的有效清单仍可复用。
原厂清单和引擎代码都参与切换缓存标识，修正后的清单不会命中旧的少槽位负载。

HyperOS 缺少确切字重锚点时，检查暂存区可信源的真实可变轴，仅在 `wght`
范围包含目标时生成对应实例并复用；不直接把可变 Regular 文件伪装成粗体。
静态源、没有 `wght` 轴或范围不包含目标时继续保留原厂对应字重。

模块和 App 版本号保持不变，沿用 Test1/Test2/Test3 的原 Debug APK。
不改变下一启动生效、暂存验证及原子提交方式。

## 验证

四种真实字体布局的完整扫描对照均为 Test2 2 槽 → Test3 1 槽 → Test4 2 槽：

- 命名 `sans-serif` 带 `lang=en`；
- 同一中文 OTF 分别由 `zh-Hans`、`ja`、`ko` 引用；
- 同一 family 使用 `lang="zh-Hans ja ko"`；
- 英文字体使用 `lang=en-Latn`。

兼容性回归同时覆盖未知西文语言、带 ASCII 的独立 Arabic/Hebrew/Thai 字体、
受保护用途、共享 TTC 的字体面、旧 v7 清单恢复，以及专用文件名提前排除、
同字体多引用仅解析一次。

扫描兼容性 16 项、HyperOS 度量 24 项、CJK 路由 27 项、ROM 保留传递 4 项
通过。字重测试验证实际 `gvar` 字形坐标变化、跨分区复用一次实例、其他轴固定、
静态/超范围保护、组合结果的源优先级和失败清理。实际 HyperOS 映射器回归恢复
3 个可映射槽，缺字重保护清单为空。以上均为宿主机测试，未替代真机结果。

最终 `scripts/build.sh` 通过，包含完整 `scripts/check.sh`。扫描的 Unicode 脚本
数据在实际读取字体时才加载，策略校验入口无需额外加载该数据。

## 计数说明

原厂扫描的槽位数与覆盖页的“可替换”不是同一个统计：覆盖页会扣除当前源字体
无法提供真实对应字重、框架动态别名及其他保持原厂的项。缺字重保护应依据当前
暂存负载和实际源能力，不能为了增加计数把 Regular 强行当作所有字重。

## 真机验证

本次对照针对可重复构造的 ROM 字体布局。尚无本次手机的原厂清单或覆盖报告，
无法确认该设备减少的全部原因，也不宣称已经验证所有机型。

刷入后完整重启，重新应用字体，再重启核对覆盖结果。若仍有数量差异，在覆盖页
导出 `/sdcard/LuoShu/reports/LuoShu-font-coverage.json`，据实际路径区分漏检、
缺源字重和保留项目。选择系统默认字体并重启，或停用模块并重启可恢复原厂。
