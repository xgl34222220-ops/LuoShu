# Test10：减少首次换字体的重复生成

Test9 的用户反馈为 `82/133 个文件，已用 247 秒`，正在处理
`NotoSansCJK-Regular.ttc（字体面 1/5）`。这说明首次生成仍然过慢，
此前相同组合再次应用的缓存耗时不能回答该问题。

本次保留完整扫描和所有目标路径，减少各路径之间重复的字形准备、合并和临时文件读写。
仅凭截图不能判断用户清单中哪些具体路径无用，也没有通过删槽位减少工作量。

## 修改

- 多个英数目标需要不同原厂保留字形时，先从大型中文组合源生成一次小型英数字库。
  每个目标仍按自己的字符范围精确裁剪，保留自己的布局和度量。
  完整来源继续用于持久化证明和后续中文补齐，不会被小字库覆盖。
- 同一 TTC 中，只有原厂 CFF、来源、替换字符范围和保留字形顺序完全一致时，
  才复用已验证的合并轮廓。各字体面的 cmap、异体字、布局、横纵度量继续独立处理。
  缓存损坏或来源变化时重新生成。
- CFF 布局合并的临时文件只携带实际所需的表和明确的字形编号顺序，
  避免反复保存、打开随后会被丢弃的大型轮廓表。完整轮廓在最终验证前恢复。
  临时文件不会作为系统负载提交。
- 小文件按批次回收对象，大型字库仍及时回收；来源摘要和字符事实在本次请求内有界复用。
- 小字库仍精确裁剪，避免接近完整覆盖时跳过裁剪而多带无用字形。

没有增加原生可执行组件，没有修改超时上限，没有更换 App，也没有增加 ROM 文件名白名单。

## 首次生成对照

使用模块内 FontTools 4.63.0、同一主机和同一合成清单，从空输出目录分别运行
Test9 提交 `2fa0a1aaed8548106e6138bc5a8fe4df1f61ba87` 和 Test10。
清单由真实字体构建：80 个具有不同拉丁字符范围及保留希腊文／阿拉伯文字形的 DejaVu 子集，
加上同一个真实五面 Noto Sans CJK 集合的 53 个路径别名。源字体为约 4.9 万字形的 Noto TTF。
这是可复现的合成清单，不是用户手机导出的 133 个文件。

| 指标 | Test9 | Test10 |
| --- | ---: | ---: |
| 清单字体首次生成 | 105.30 秒 | 75.12 秒 |
| 80 个英数目标的补齐调用合计 | 15.25 秒 | 4.15 秒 |
| 峰值 RSS | 974.46 MiB | 832.63 MiB |
| 成功映射路径 | 133 | 133 |
| 不同输出字体面 | 85 | 85 |

首次清单生成耗时下降约 28.7%。英数调用合计不包含共用小字库的前置准备，
整体 75.12 秒包含该准备。TTC 的五个字体面有四个复用合并轮廓。
没有使用最终输出缓存来冒充首次生成速度。

逐一比较 133 个目标路径对应的 81 组不同输出文件、85 个字体面，共 1520 项 SFNT 表：
仅忽略 `head.checkSumAdjustment`、`head.created`、`head.modified`，其余表内容全部一致。
因此不能声称完整文件逐字节一致；字符、轮廓、布局和度量表内容的对照没有差异。

可用 `scripts/inventory_font_bulk_benchmark_fixture.py` 准备清单，
再用 `scripts/inventory_font_stage_benchmark.py` 运行。字体由调用者提供，不在仓库或模块内附带。

## 验证范围与限制

回归覆盖大型中文源的英数预处理、完整源证明保留、区域 TTC 独立布局、缓存损坏回退，
以及小字库接近完整覆盖时的无用字形裁剪。完整 `scripts/build.sh`（包含 `scripts/check.sh`）
通过，Python 测试执行共 717 项，配套 Shell 检查通过。补齐引擎 32 项测试全部通过。

本次没有连接 Android 实机，也没有取得用户的“花轮丸”和“鸿蒙保时捷”原始字体文件。
75.12 秒只包括主机清单字体生成，不包括组合源生成、设备刷入、重启及运行时挂载，
不能据此承诺手机首次换字体在一分钟内完成或已兼容全部机型。
沿用 Test9 的字形容量边界处理：超限时，已选择替换且来源缺少专用异体字的序列可使用来源常规字形，
逐项记录回退；未选中的原厂异体字继续保留。没有改变这一行为。

测试包沿用 Test8 的“洛书测试版”App，仅升级模块脚本。未合并主分支，未发布正式版本。
