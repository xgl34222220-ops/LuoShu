# v4.3.0 运行时修复依据

## 基线与占用

功能基线是 v4.2.0。模块管理器显示的 GB 数字是目录存储占用，不能据此推定进程 RAM。

旧 HyperOS 广泛匹配 NotoSans*，将多个无关语言槽生成独立中文字体；只删 cmap 并不移除 outlines。新版本收窄 UI 目标，进行真实子集化，在生成可变字重前去掉未使用字形，共享相同度量的生成结果。源文件只读。详见同目录 v4.3.0-storage-benchmark.json，数据是受控主机基准，不是手机测量。

升级时保留当前有效载荷，跳过不兼容生成缓存并登记显式重新应用要求。启动确认不能提前清除此标记，避免升级后再次复用旧大字体树。

## Google 字体路径

[Google 官方文档](https://developers.google.com/fonts/docs/android)说明 Play Services 提供独立的下载字体 Provider，因此系统扫描的槽位数并不能表示这条路径的覆盖程度。

[Chromium AndroidFontLookupImpl](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/public/android/java/src/org/chromium/content/browser/font/AndroidFontLookupImpl.java)的 tryFetchFont 使用 mFetchedFontCache 保存 ParcelFileDescriptor，并对后续请求 dup 已有描述符。推论：修复路径上的 bind mount 不能替换当前 Chrome 已经持有的旧字体描述符，必须分别处理路径维护与已有消费者缓存。

HyperOS 还存在主题生成的动态字体路径。适配必须追踪路径、目标 inode 和进程挂载环境变化，不能只在开机扫描一次。空闲维护只检查元数据；无变化不启动字体解析与生成。

[AOSP ActivityManagerShellCommand](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ActivityManagerShellCommand.java) 的 runKill 调用后台进程回收 API，[ActivityManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ActivityManagerService.java) 按进程重要性筛选后台进程。

已有消费者使用 PID、进程启动时间及 bootId 标识；只有 fd/maps 仍引用旧字体 device/inode 时才排队，按 UID 区分 Android 用户。使用 ActivityManager 的后台进程回收而非 force-stop，前台进程保留待刷新项，下次转入后台后重试。旧进程退出、已无旧字体引用、关闭模块或恢复默认均移除待刷新项；调用频率和单次等待有上限。

这不能改写正在使用中的 Typeface/文件描述符；前台界面的效果不会凭一次挂载立即重新排版。真机结果仍需核实，不能推定所有 Google App 或所有网页使用同一字体入口。

## 状态查询

App 状态只使用本次启动已有验证记录，不在连接查询中执行全字体校验；粗细状态只查询一次 Settings，跳过字体目录迁移。状态页不承担字体重建。
