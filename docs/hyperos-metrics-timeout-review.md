# HyperOS 字体偏移与应用超时修复检查

基线：86c7c341d2fce193d95af82f1d83d273b60f437a（v4.0.0）。

## 已复现的问题

- 旧暂存脚本把 hhea 上下限固定为 0.98/0.30，原厂要求 1.10/0.35
  时也会被截断。原厂 OS/2 与行距也没有完整保留。
- 开机 `hyperos_clock_compat.sh` 会把 product 等分区已处理的同名字体
  覆盖为 system 分区的版本。使用两个不同分区度量的夹具，旧代码失败，
  修复后保持文件内容不变。
- 单字体任务在 76% 进入 HyperOS 补齐。旧逻辑对每个目标调用 shell，
  对每组字体重新启动 Python，度量修改还会加载和重编译字形。
- 单字体和复合字体调用方都可能忽略 HyperOS 补齐失败并继续提交。
- 原有暂存源选择会漏掉 700.ttf 等实际多字重来源，退回 regular。

## 修改

- 使用一个 Python 进程批量生成，保留原厂 hhea、OS/2、行距与度量选择位；
  缓存键包含完整合约，避免 hhea 相同、OS/2 不同的槽位混用。
- 不解析、变换或重编译字形轮廓，保持 glyf/CFF/gvar 原始数据。
  保留用户字体的 head 边界；不靠伪造字形边界压缩排版。
- 在替换任何目标之前生成所有源/合约组合，避免把本轮输出再次当作输入。
- 开机兼容修补只填缺失槽位；已有分区字体不再被覆盖。
- 源字体/度量处理错误阻止提交。超时提示增加最后阶段，默认超时未延长。
- 新文件加入正式模块打包清单，旧的固定比例文本断言换为实际行为测试。

## 验证

- 8 项新增测试通过：原厂完整度量、字形保持、多字重与缓存隔离、
  输入稳定、无清单回退与坏字体失败、开机保留、活动负载保护、
  双调用方错误传播、单进程 shell 入口（部分在同一测试方法中）。
- 现有重复切换/开机激活、34% 任务推进、复合提交竞态、HyperOS 映射、
  ColorOS 分区、OriginOS/Flyme、原厂读取保护、v3 扫描与后台超时测试通过。
- 旧 scannerRevision=2 扫描测试在基线和本分支均失败，因为当前扫描器是 v3；
  对应 v3 测试通过。没有将这项已有失败列为本次修复。
- 宿主机 DejaVuSans 759720 字节、6 组合约：旧处理 2.048 秒，新处理
  0.246 秒（约 8.3 倍）。不包含 Android/Root/存储与 CJK 大字体开销，
  不能推断所有手机都能一分钟内完成。

## 尚待真机核实

本文记录发布前的检查，检查时尚未刷入手机。没有这次用户反馈设备的完整任务日志，不能
认定所有超时都由 HyperOS 阶段引起。原厂清单缺失/过期时明确记录紧凑
回退，并不代表实现了逐槽原厂度量。字体自身的字形边界、App 自带字体、
字体选择缓存和 ROM 的渲染实现仍可能导致显示差异。
