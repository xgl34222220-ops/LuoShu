# HyperOS 英数覆盖：已确认的规则回归

基线：v4.3.0 / main `fe4df5f224dca9bc77517ffa539ba021ed4b1a8e`。
本次用户反馈：HyperOS 多处英文、数字再次没有覆盖。

## 代码中已确认的问题

v4.3.0 将宽泛的 NotoSans 匹配改为较小的白名单，同时遗漏了 Mono、Display、Condensed 和部分 VF 名称，以及 DroidSansMono / DroidSansFallback。Python 扫描/构建策略和开机 Shell 映射均拒绝这些名称；构建器还会清除白名单之外的暂存覆盖文件。与 v4.2.0 对比可以确认这些名称的策略收窄。

另一个既有问题：不区分单词的 `icon` 子串过滤会误伤 `SemiCondensed`。这是代码测试复现，不是已观察到用户手机使用了某一个 SemiCondensed 字体。

## 修改

- 仅补回明确的正常 UI 字体族，匹配完整族名或以连字符分隔的样式，不恢复无差别的 NotoSans* 复制。
- Python 与 Shell 同步修正；SemiCondensed 不再误判，附加 Icon/Icons 的名称仍排除。
- 继续排除无关语言、Emoji、图标、斜体及 TTC；新增族名不会通过相似前缀吞入其他语言。
- HyperOS 扫描覆盖修订从 3 提升到 4，旧清单进入既有的可信原厂重扫流程；ColorOS 不因这次修订被强制重扫。
- 不改字体子集压缩、结果复用、主题动态入口、Google 下载字体维护、挂载事务和版本号。

原有更新逻辑会比较这两份字体构建规则文件，拒绝复用规则变化前的生成缓存。当前活动字体不在本补丁中直接删除或改写；完成库存刷新后，重新应用字体才能生成采用新规则的负载。

## 验证边界

本地通过 9 项有针对性的单元/策略测试，实际调用 Shell 的名称判定与目录枚举，并执行从扫描器提取的纯缓存修订判断。包含恢复入口、现有英数/中文/时钟入口、语言与图标排除、TTC/斜体保护、路径校验、去重、动态入口以及旧库存修订检查。相同测试对未修改的 v4.3.0 会失败。

这些文件名是明确标注的测试夹具，不是本次读取的 K80 字体清单。未取得当前漏字体页面的进程字体路径，也没有 K80 至尊版/一加 15 的连接真机。本地结果不代表 Android 构建、整机体积、重启稳定性或所有英数页面已验证；没有据此创建新正式版或预发行版。
